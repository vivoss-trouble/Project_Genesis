# Genesis v5.7 Multi-Marker Detector

v5.7 separates visual topology extraction from tactical decision making. It does
not add a decision layer. It only proves that the vision path can extract a
stable target set from one controlled native window.

## Boundary

- `genesis-core` is unchanged.
- `genesis-os-driver` is unchanged.
- The v5.5 single-shot gate remains compatible.
- Selection is deterministic and minimal: the legacy `marker_detection` field is
  the first candidate in left-to-right order.
- No policy, priority, semantic target selection, or retry logic is introduced.

## Native Dummy Target Set

The Native Dummy now renders three controlled targets:

```text
native-heal-a
native-heal-b
native-heal-c
```

Each target owns one magenta marker and an independent hit counter. The legacy
fields still point at the center target to preserve v5.3-v5.6 compatibility.

## Retina Output

`genesis-frame-grabber` now emits:

```json
{
  "marker_candidates": [
    {
      "candidate_id": "marker-0",
      "pixel_center": {"x": 200.0, "y": 324.0},
      "coregraphics_logical_center": {"x": 100.0, "y": 162.0},
      "appkit_logical_center": {"x": 100.0, "y": 130.0},
      "bbox": {"x": 172, "y": 296, "width": 56, "height": 56},
      "pixel_count": 3136
    }
  ]
}
```

Candidates are produced by connected-component analysis over the deterministic
magenta threshold:

```text
R >= 200, G <= 120, B >= 200
```

The list is sorted left-to-right for reproducible dry-run selection.

## Validation

```bash
./scripts/validate_v57_multi_marker_detector.sh
```

The validation remains dry-run only. It asserts:

- window-scoped capture
- at least three marker candidates
- bbox, centers, and pixel counts for each candidate
- deterministic left-to-right ordering
- transformed action point exists
- OS-driver receipts remain `posted=false`

## Next Boundary

v5.8 may introduce a decision layer such as:

```text
Target Set -> Selection Policy -> Fire-at-ID
```

That layer must consume `marker_candidates` instead of raw pixels.
