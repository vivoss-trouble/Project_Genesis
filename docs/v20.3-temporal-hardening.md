# Genesis v20.3 Temporal Hardening

v20.3 hardens the evidence ledger time axis before public deep-water execution.
It upgrades v20.1 evidence packs with endogenous timestamp fields and upgrades
v20.2 replay verification so sealed time-tear checks can become fatal.

## Ledger Additions

Every JSON evidence slice now receives:

- `sealed_utc_timestamp_ms`
- `evidence_write_order`
- `evidence_schema_version: v20.3-temporal-hardening`

The manifest now includes:

```json
{
  "schema_version": "v20.3",
  "temporal_hardening": {
    "schema_version": "v20.3",
    "sealed_step_timestamps": true,
    "timestamp_field": "sealed_utc_timestamp_ms",
    "order_field": "evidence_write_order",
    "time_source": "ledger_materialization_utc"
  }
}
```

## Replay Rule

When sealed timestamps are available, v20.2 enforces:

```text
pre_remap.sealed_utc_timestamp_ms
  <= driver_receipt.sealed_utc_timestamp_ms
  <= post_assert.sealed_utc_timestamp_ms
```

and:

```text
driver_receipt.sealed_utc_timestamp_ms - pre_remap.sealed_utc_timestamp_ms
  <= GENESIS_V202_TIME_TEAR_THRESHOLD_MS
```

Default threshold: `1000ms`.

## Compatibility

Legacy v20.1 packs without sealed step timestamps remain valid evidence packs.
They continue through replay with advisory mtime telemetry only.

## Redline

Validation creates a copied evidence pack, edits the sealed timestamp to exceed
the threshold, recomputes the manifest hash for the edited files, and verifies
that replay fails with:

```text
TIME_TEAR_VIOLATION
```
