# Genesis v9.9 Open-Web AX Key Route Armed Report

## Command

```bash
GENESIS_V99_ARMED_CONFIRM=GENESIS_V99_ARMED_OPEN_WEB_AX_KEY_ROUTE \
GENESIS_V99_AUTO_KEY_CONFIRM=GENESIS_V99_AUTO_KEY_ROUTE_PROBE \
./scripts/run_v99_open_web_ax_key_route_probe.sh
```

## Target

- URL: `https://doc.rust-lang.org/book/`
- Browser: Safari
- Restricted key: `page_down`

## Result

The v9.8 AX focus step remained clean:

```json
{
  "ax_success": true,
  "url_changed_after_focus": false,
  "window_id_stable": true,
  "focus_visual_change_detected": false
}
```

The restricted key posted successfully, but did not move the web content:

```json
{
  "requested_key": "page_down",
  "key_posted": true,
  "url_changed_after_key": false,
  "key_visual_change_detected": false,
  "key_absorbed_by_content": false
}
```

## Interpretation

v9.9 improves the v9.7 failure mode: after AX focus, `page_down` no longer
escaped into Safari chrome or changed the front URL. That is a real routing
improvement.

However, the key still did not produce visible page displacement. The event was
posted at the OS layer, but WKWebView did not absorb it as a content scroll. The
hunter controller must still not consume keyboard scrolling.

The remaining gap is no longer "wrong battlefield" routing. It is now
"web-content first responder" routing inside Safari.

## Next Cut

The next probe should target the inner web content focus boundary, not the outer
Safari window shell. Candidate approaches:

- inspect the Safari AX tree for a focused `AXWebArea`,
- set the focused UI element to the web area if exposed,
- verify with the same single-key URL lock and Shadow Map court.
