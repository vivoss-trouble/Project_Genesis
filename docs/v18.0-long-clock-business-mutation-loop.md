# Genesis v18.0 Long-Clock Business Mutation Loop

## Purpose

v18.0 combines the v15.0 long-clock pagination loop with the v16/v17 business
mutation vocabulary inside a deterministic local fixture. The goal is to prove
that business-state mutation can occur inside each pagination step without
polluting the main loop clock, URL assertions, or next-step remap.

The fixture deliberately uses the symmetrical "Groundhog Day" formation:
Page 0, Page 1, and Page 2 expose the same modal, text field, checkbox, commit
button, and `Next chapter` target. This stresses ghost focus, stale form state,
and cross-page cache leakage.

## Pipeline

```text
Page N
  -> modal collision on Commit profile
  -> ISR clearance via Close
  -> fresh remap
  -> text mutation
  -> checkbox mutation
  -> business commit
  -> business state assertion
  -> fresh remap of Next chapter
  -> pagination click
  -> Page N+1
```

After Page 2, Page 3 intentionally has no `Next chapter`. That absence is the
legal terminal condition.

## Red Lines

- Dry-run must stop at the first projected physical business mutation.
- Armed validation must run serially because macOS GUI focus is a singleton.
- ISR state must not increment the main pagination step.
- Every business mutation step must use fresh remaps after clearance and before
  pagination.
- A business subprocess must return booleans and receipts, not reusable DOM or
  AX references.
- The final terminal condition must be `target_not_found_terminal_ok`.
- v18.0 does not re-prove combobox mechanics; v17.0b owns the Z-axis combobox
  primitive. v18.0 records that inheritance and focuses on long-clock isolation.
