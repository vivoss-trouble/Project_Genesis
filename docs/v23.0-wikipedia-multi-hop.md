# Genesis v23.0 Wikipedia Multi-Hop

v23.0 extends the Wikipedia post-search path from a single mutation-and-extract
cycle into a two-hop public navigation chain:

1. search Wikipedia for `OpenAI`
2. extract the resulting article facts
3. plan a deterministic internal Wikipedia link to `微软` / `Microsoft`
4. click that link with a fresh remap-derived point
5. extract the second article facts

## Planning Contract

The v23 planner is read-only. It does not post OS input and does not reuse stale
coordinates from the previous page. It scans the current AX tree after the
OpenAI page has loaded and filters candidate links by:

- exact target text: `微软`
- alternate target text: `Microsoft`
- domain lock: `wikipedia.org`
- visible frame intersecting the active Safari window
- approximate main-content region after the article title

If multiple candidates survive, the stable tie breaker is
`main_content_first_y`, which selects the first candidate by physical Y position
inside the main content flow. The planner records candidate counts, survivor
counts, selected point, selected URL, and the tie breaker in the evidence pack.

## Execution Contract

The runner keeps the v20 rule intact: the plan is intent, not authority. The
second-hop click point is accepted only from the immediate v23 pre-remap ledger
slice, and the driver receipt must follow that slice in the sealed write order.

The expected armed summary includes:

- `multi_hop_step_count: 2`
- `first_extraction_asserted: true`
- `internal_link_plan_ready: true`
- `internal_link_tie_breaker: "main_content_first_y"`
- `second_click_posted: true`
- `second_url_changed: true`
- `second_extraction_asserted: true`
- `sequence_complete: true`

## Extraction Note

v23 also hardens the v22 result extractor for non-Latin Wikipedia titles. The
normalizer now preserves Unicode letters and numbers, so Chinese targets such as
`微软` remain assertable after fresh remap. This keeps `result_title_found` tied
to the physical AX/window state rather than to an ASCII-only text assumption.
